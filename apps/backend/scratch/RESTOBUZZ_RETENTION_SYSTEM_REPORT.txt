1. OBJECTIVE
------------
To transform the RestoBuzz CRM from a static member list into a dynamic, behavior-aware retention powerhouse. The system now automatically tracks member visit history from ReserveGo and segments them into actionable behavioral tiers (Active, At-Risk, Dormant, Lost) for high-ROI marketing campaigns.

2. CORE ARCHITECTURE: MULTI-DATABASE BRIDGE
-------------------------------------------
The system supports a hybrid multitenant architecture:
- LOCAL DB (MongoDB): Primary store for Soraia (r1), Gigi (r3), S.H. Bandra (r4), S.H. Juhu (r5), and Sweeney (r6).
- EXTERNAL CLUSTER (Fielia r2): Bridges to an external MongoDB instance (test.cards) for Fielia members.
- UNIFIED SERVICE LAYER: The 'MemberMatchService' abstracts this complexity, allowing all other services to query members without knowing where the data lives.

3. DATA MODELS & SCHEMA UPDATES
-------------------------------
The 'members' collection (and Fielia 'cards') now includes these production fields:
- normalized_phone (string): Canonical E.164 format (+91...) for perfect matching.
- last_visit (ISODate): The definitive timestamp of the guest's most recent visit.
- dormancy_tier (string): Enum [ACTIVE, AT_RISK, DORMANT, LOST, UNKNOWN].
- last_synced_at (ISODate): Timestamp of the last successful visit mapping.

4. DORMANCY TIER LOGIC (THRESHOLD DEFINITIONS)
----------------------------------------------
Tiers are calculated based on the delta between 'today' and 'last_visit':
- ACTIVE: 0 - 30 days (Regular visitors, maintain engagement).
- AT_RISK: 30 - 60 days (Missing their usual cycle, prime for reminders).
- DORMANT: 60 - 90 days (Lost habit, requires a strong reactivation offer).
- LOST: 90+ days (Churned, requires deep win-back incentives).
- UNKNOWN: No visit history found in ReserveGo imports.

5. BACKEND SERVICES (THE ENGINE)
--------------------------------
- PhoneNormalizer:
  * Removes spaces, hyphens, and Excel artifacts (.0).
  * Enforces +91 prefix and validates length (8-16 digits).
  * Critical for joining 230k+ guest records with 2k+ members.

- MemberMatchService:
  * Routes queries between 'restobuzz.members' and 'fielia_external.test.cards'.
  * Handled the r2 identity resolution gap (1,165 members now visible).

- DormancySyncService (Production Grade):
  * INCREMENTAL: Uses 'sync_state' to track the last processed '_id'. Never reprocesses old data.
  * WRITE-OPTIMIZED: Uses conditional filters to only update a member if their tier has changed or a newer visit is found.
  * ATOMIC: Uses $max for visit date updates to ensure idempotency.

6. OBSERVABILITY & RESUMABILITY
-------------------------------
- sync_state collection:
  * Fields: restaurant_id, source, last_processed_id, last_sync_time, status.
  * Purpose: Ensures syncs can be resumed after server restarts or failures.
  
- sync_logs collection:
  * Fields: duration, processed_records, matched_records, tier_changes, failed_records.
  * Purpose: Provides an audit trail for system health and recovery tracking.
